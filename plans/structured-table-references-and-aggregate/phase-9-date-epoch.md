## Design decision

**What differs today.** MySheet converts through .NET's OLE Automation date (`DateSerial.cs`, epoch 1899-12-30 = serial 0), so serial 1 is 1899-12-31 and serial 60 collapses onto 1900-02-28. Excel's 1900 system has serial 1 = 1900-01-01 and a phantom 1900-02-29 at serial 60. **Measured: the two systems agree numerically from serial 61 (1900-03-01) onward** — `DATE(2024,3,15)` = 45366, `MONTH/DAY/WEEKDAY(45366)` = 3/15/6, `TEXT(45366,"yyyy-mm-dd")` = 2024-03-15, `INT(TODAY())-DATE(2026,9,9)` = 0 on both engines. Exactly the serials `[0, 61)` differ, plus every function that COUNTS across that window (a span that includes serial 60 is one day longer in serials than in the Gregorian calendar).

**Two assumptions in this phase's brief are wrong and Aspose overrules them.** (1) `DATE(1900,2,29)` is **61**, not 60: Aspose's `DATE` builds a proleptic-Gregorian date and rolls Feb 29 1900 to Mar 1 (`DATE(1900,2,30)` = 62, `DATE(1900,3,0)` = 59). Serial 60 is reachable only by arithmetic (`DATE(1900,2,28)+1` = 60) and by `DATEVALUE("1900-02-29")` = 60. (2) Serial 60 is **not** "1900-02-29 for DAY/MONTH/YEAR": `DAY(60)` = 28, `WEEKDAY(60)` = `WEEKDAY(59)` = 3, `EDATE(60,0)` = 59 — the calendar functions collapse 60 onto 59. Only the number FORMATTER (`TEXT`, cell display) and the 30/360 day counts show a Feb 29.

**Aspose's model, as measured, is three calendars, and the design names all three so that each function is pinned to the one it uses.** (a) **The DateTime map** (`CellsHelper.GetDateTimeFromDouble`, measured: 0 → 1899-12-31, 1 → 1900-01-01, 59 → 1900-02-28, 60 → 1900-02-28, 61 → 1900-03-01; the inverse `GetDoubleFromDateTime`: 1899-12-31 → 0, 1900-01-01 → 1, 1900-02-28 → 59, 1900-03-01 → 61; `PutValue(new DateTime(1899,12,30))` throws — a negative serial is unrepresentable). In OADate terms: `ToDateTime(s) = FromOADate(s < 60 ? s + 1 : s)` and `FromDateTime(d) = d.ToOADate() - (d < 1900-03-01 ? 1 : 0)`, so serial 60 is never produced from a `DateTime` and the time fraction rides along unchanged (`DateTimeValue` of 60.5 = 1900-02-28 12:00). Used by YEAR/MONTH/DAY (with a day-zero rule: any serial in `[0,1)` is "1900-01-00" → 1900/1/0), EDATE, EOMONTH, WEEKNUM, ISOWEEKNUM, NETWORKDAYS(.INTL), the bond/coupon family, DATEDIF's calendar units, `DATE`'s inverse, the xlsx loader and `EpochNow`. (b) **The Lotus weekday**: `WEEKDAY(s)` = `((⌊s⌋ − 1) mod 7) + 1` with 60 collapsed onto 59 — i.e. exactly what `FromOADate(s).DayOfWeek` gives today for s ≤ 59 (that is why `WEEKDAY(1)` = 1 already matches) — used by WEEKDAY, `TEXT`'s `ddd`/`dddd`, and the remainder walk of WORKDAY. (c) **The Lotus calendar** (60 = 1900-02-29, 0 = 1900-01-00, February 1900 has 29 days) used by `TEXT`'s numeric date fields and by the 30/360 arithmetic of DAYS360 and YEARFRAC, and by serial subtraction wherever Excel counts days (DAYS, DATEDIF `d`/`md`/`yd`, YEARFRAC bases 1-3, XNPV/XIRR).

**One central conversion.** `Danfma.MySheet/Expressions/DateSerial.cs` stays the single owner. It gains the map above in `ToDateTime`/`FromDateTime` (calendar (a)), `TryGetCalendar(serial, out year, out month, out day)` (calendar (a) plus the day-zero rule; the callers that need the phantom pass `phantomFeb29: true` and get 1900/2/29 for `[60,61)`), and `LotusDayOfWeek(serial)` (calendar (b)). `FromComponents` calls `FromDateTime` and keeps its `< 0 → #NUM!` guard, which is what turns `DATE(1900,1,-1)` into `#NUM!` and `DATE(1900,1,0)` into 0. `MaxSerial` is unchanged (2958465 = 9999-12-31 on both engines; `DAY(2958466)` = `#NUM!` on both).

**Smallest change, measured.** The prototype of item 2 plus the day-zero rule, the Lotus WEEKDAY, serial-subtraction DAYS and the loader — six files, ~20 lines — turns **104 of the 187 mismatching rows green and flips ZERO existing tests** (core still 1377/1393 with the same 16 Phase 8 RED pins; Excel 90/90). The remaining 151 mismatches (83 still wrong plus 68 that the map ALONE regresses — every one a day-counting function) are exactly the per-function items 4-12, and they are per-function because Aspose is: NETWORKDAYS counts serial 60 as a Wednesday (`NETWORKDAYS(59,61)` = 3) while WORKDAY skips nothing and DAYS360 calls it Feb 29. `DateConstructionTests.Serial60_Is1900LeapYearLimitation` keeps passing because Aspose ALSO answers `DAY(60)` = 28 — the test's name and comment are what lie, not its assertions (item 15).

**Three generic divergences surfaced by the modern-date controls are recorded, not fixed here** (they are P0 work items for the master plan's open-decisions list): `ACCRINT(DATE(2023,2,28),DATE(2023,6,30),DATE(2023,3,1),0.1,1000,2)` = 0.8333 in Aspose vs 0.2778 here (no start-of-February rule in Aspose's accrual days); `YEARFRAC(DATE(2023,1,1),DATE(2024,1,1),1)` = 1 vs 0.99863 (basis-1 denominator across a year boundary); `TEXT(61,"d")` = 1 vs `03/01/1900` (a lone `d`/`m` is a .NET standard-format string in `ExcelDateFormat.ToDotNet`) and `TEXT(60,"[$-409]mmmm d, yyyy")` prints the locale tag literally. `EOMONTH(2958465,0)` = `#NUM!` in Aspose vs 2958465. `SUM(MONTH({1,2,3}))` is a `ParseException` — array literals are a parser gap outside this plan. The DAYS360 February-end divergence is ALSO generic but is a prerequisite for this phase's 1900 rows, so it is fixed in item 10 with its modern controls pinned.

## Risks carried by this phase

- **Every stored serial below 61 changes meaning by one day.** A workbook that persisted `=DATE(1900,1,1)`'s cached value (2) or a literal 2 meant as 1900-01-02 now reads it as 1900-01-02 / 1900-01-03. No wire byte changes, so nothing can detect it mechanically; the only mitigation is item 14's note and the changelog. Real-world data below 1900-03-01 is rare (the Microsoft page says so too), which is also why no existing test moved.
- **The change touches every date-function golden in the suite by construction** — 14 + 13 + 8 + 3 date tests plus 2 bond/cash-flow suites. Measured: none flips, because all use dates ≥ 2001 and the two maps coincide there. That protection is only as good as the "serials ≥ 61 are identical" invariant in item 2; a typo in the `< 60`/`< 1900-03-01` boundaries moves EVERY modern date by one day and the suites will catch it loudly.
- **Item 9 changes DAYS360 for modern dates too** (end-of-February rule removed). It is Aspose-measured and generic, but it contradicts the Microsoft DAYS360 page, and a user with a 30/360 accrual on a February-end date will see a different number. It ships under `feat(eval):` with the modern controls pinned; it must be named in the changelog explicitly.
- **Item 8 reproduces an Aspose implementation artifact** (two weekday calendars inside WORKDAY, selected by `days`). It is confined to serials ≤ 60, isolated in `Advance`, and fully pinned; but it is the one item where "match Aspose" and "match Excel" may differ, and the user's ruling is what settles it, not this plan.
- **`TEXT` stops using `DateTime.ToString` for the date part.** Day 0 and Feb 29 1900 are not representable in `DateTime`, so the tokens must be substituted by hand; the risk is a regression in a format code the tests do not cover (`TextFormatTests` has 3 tests). Add one pin per token family (`yyyy`, `yy`, `mmmm`, `mmm`, `mm`, `m`, `dd`, `d`, `dddd`, `ddd`) on a modern date before touching the renderer.
- **The Lotus weekday must never leak into NETWORKDAYS**, and the DateTime map must never leak into WEEKDAY: `NETWORKDAYS(1,10)` = 8 and `WEEKDAY(1)` = 1 are only compatible because they use different calendars. Both are pinned; a future "cleanup" that unifies them will break one.
- **Phase ordering.** Item 15a edits a Phase 8 test; landing this phase first leaves Phase 8's pin RED for the wrong reason. Rebase on Phase 8.

## Open questions owned by this phase

Aspose answered every row it was asked. What remains is only what its answers do not settle:

- **Lone `d`/`m` `TEXT` formats.** Measured `TEXT(0,"d")` = 31, `TEXT(0,"m")` = 12, `TEXT(60,"d")` = 28 (the DateTime-map fields) while `TEXT(0,"dd")` = `00`, `TEXT(0,"m/d/yyyy")` = `1/0/1900`, `TEXT(60,"dd")` = 29 (the Lotus calendar).
